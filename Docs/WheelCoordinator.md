# WheelCoordinator Design

`VehicleWheelCoordinatorComponent` is a chassis-level coordination component.
It is automatically found or generated by wheels, axles, drive assemblies, and
aero components when they attach to the same physical parent.

Despite its name, it is not the component that drives wheel physics. Wheel
physics remains under `VehicleWheelComponent`, `VehicleAxleAssemblyComponent`,
and `VehicleDriveAssemblyComponent` because drivetrain update order is part of
the physics model.

## Main Responsibilities

`WheelCoordinatorComponent` coordinates data that belongs to the whole chassis
rather than to one wheel:

- It registers wheels attached to the same chassis.
- It recalculates static sprung mass when wheel layout, chassis mass, or center
  of mass changes.
- It registers axles and updates wheelbase reference data.
- It provides aggregate vehicle dimensions such as minimum turning radius,
  maximum track width, and maximum wheelbase.
- It registers aero components and updates them together against the same
  chassis state.

The coordinator exists so components can remain modular while still sharing
vehicle-level information.

## Why It Does Not Update Wheel Physics

Wheels are part of the drivetrain solve. During each drive assembly substep,
torque, angular velocity, and reflected inertia must be exchanged in a strict
order:

```text
Clutch / gearbox torque
  -> transfer case
  -> axle differential
  -> wheels

Wheel angular velocity and wheel inertia
  -> axle differential
  -> transfer case
  -> gearbox input shaft
  -> clutch model
```

If `WheelCoordinatorComponent` updated wheels independently, it could break this
ordering. For example, a wheel might be advanced before the differential has
distributed torque, or after the gearbox has already sampled downstream inertia.

This is different from aero components. Aero components mostly need shared
chassis state, such as velocity, angular velocity, center of mass, and transform.
They can be evaluated as a batch and their impulses can be accumulated once.
Wheel components, however, are part of the bidirectional drivetrain update.

## Sprung Mass Updates

Each wheel has a static sprung mass used by the suspension model. This value
depends on the chassis mass, center of mass, and designed wheel positions.

The coordinator tracks when sprung mass should be recomputed:

- A wheel is registered.
- A wheel reports that its designed hub location moved.
- The chassis center of mass changes.
- The refresh interval elapses and dirty data is detected.

When sprung mass data is dirty, the coordinator solves a static load
distribution problem:

- With one support point, the wheel receives all chassis mass.
- With two support points, mass is distributed along the line between them.
- With three or more support points, the solver distributes mass while
  satisfying total mass and moment-balance constraints.

If the solver cannot find a valid distribution, the coordinator falls back to an
even mass split across registered wheels.

## Wheelbase Reference

Axles register with the coordinator so wheelbase-related values can be updated
from all axles on the same chassis.

The current implementation computes the average center of registered axles, then
uses each axle's distance from that center to estimate a wheelbase reference.
Axles use this reference for steering calculations such as Ackermann steering.

This works well for common four-wheel layouts. For unusual vehicle layouts,
custom steering logic or manual validation may be needed.

## Aero Updates

Aero components also register with `WheelCoordinatorComponent`.

The coordinator updates registered aero components together:

1. Read the chassis physics handle once.
2. Read chassis transform, center of mass, linear velocity, and angular velocity.
3. Ask each aero component to calculate force and torque.
4. Accumulate the forces and torques.
5. Apply the final linear and angular impulses to the chassis.

This avoids repeating expensive or lock-sensitive chassis operations for every
aero component.

## Automatic Creation

`FindWheelCoordinator` searches under the physical chassis component. If it does
not find a coordinator, it creates one and attaches it to the chassis.

This means most users do not need to manually add a `WheelCoordinatorComponent`.
It appears as shared infrastructure once wheels, axles, drive assemblies, or
aero components need it.

## Practical Notes

- Do not call wheel physics from the coordinator unless you also redesign the
  drivetrain update order.
- If wheel positions are changed at runtime, call the relevant wheel or axle
  setup functions so the coordinator can refresh sprung mass and wheelbase data.
- If you use unusual layouts, verify the computed wheelbase and steering
  behavior.
- Aero components can safely use the coordinator because they do not participate
  in drivetrain torque and inertia propagation.

## Related Components

- `VehicleWheelComponent`: registers with the coordinator and receives sprung
  mass updates.
- `VehicleAxleAssemblyComponent`: registers with the coordinator and receives
  wheelbase-related data.
- `VehicleDriveAssemblyComponent`: controls drivetrain update order and may
  share the same coordinator.
- `VehicleAeroBaseComponent`: registers with the coordinator for batched aero
  updates.
